# 知识库用户指南

## 概述

基于 LightRAG 的知识库功能允许您从文档中构建可搜索的知识仓库。它使用先进的 RAG（检索增强生成）技术来索引文档，并基于内容回答问题。

## 快速开始

### 第一步：创建工作空间

工作空间是知识库的独立环境。每个工作空间都有自己的文档、索引和配置。

**创建工作空间：**
1. 导航到 **知识库** 标签页 → **设置**
2. 在 **工作空间配置** 部分，您会看到当前工作空间名称
3. 创建新工作空间：
   - 点击工作空间选择器下拉菜单
   - 选择"创建新工作空间"
   - 输入唯一名称（例如："项目文档"、"研究论文"）
   - 点击"创建"

**默认工作空间：**
- 如果不创建工作空间，系统使用"default"
- 可以随时切换工作空间而不丢失数据

**重要提示：**
- 每个工作空间维护自己的向量数据库和知识图谱
- 切换工作空间需要重启 LightRAG 服务
- 工作空间数据存储在 `rag_storage/<工作空间名称>/`

### 第二步：配置 LLM、Embedding 和 Reranker 模型

在上传文档之前，配置驱动知识库的 AI 模型。

#### 2.1 LLM 提供商配置

LLM（大语言模型）基于检索的上下文生成自然语言答案。

**支持的提供商：**
- **OpenAI**：GPT-4、GPT-3.5-turbo
- **Azure OpenAI**：企业级 OpenAI 模型
- **Anthropic**：Claude 3.5 Sonnet、Claude 3 Opus
- **Google Gemini**：Gemini 1.5 Pro/Flash
- **DeepSeek**：DeepSeek Chat、DeepSeek Reasoner
- **Qwen**：Qwen Max、Qwen Plus、Qwen Turbo
- **Ollama**：本地模型（Llama、Qwen、DeepSeek）

**配置步骤：**
1. 进入 **设置** → **LLM 提供商**
2. 从下拉菜单选择提供商
3. 配置提供商特定设置：
   - **API 密钥**：提供商的 API 密钥（云提供商必需）
   - **API 主机**：提供商端点（大多数提供商自动填充）
   - **模型**：从可用模型中选择
   - **最大令牌数**：最大响应长度（默认：4096）

**推荐模型：**
- **质量优先**：GPT-4、Claude 3.5 Sonnet、Qwen Max
- **速度优先**：GPT-3.5-turbo、Gemini 1.5 Flash、Qwen Turbo
- **隐私优先**：Ollama（本地运行）

#### 2.2 Embedding 提供商配置

Embedding 将文本转换为数值向量以进行语义搜索。

**支持的提供商：**
- **OpenAI**：text-embedding-3-large（1536/3072 维）、text-embedding-3-small（512/1536 维）
- **Azure OpenAI**：与 OpenAI 相同
- **Ollama**：本地 embedding 模型
- **Jina AI**：jina-embeddings-v3（1024 维）
- **Voyage AI**：voyage-3、voyage-3-lite
- **Cohere**：embed-english-v3.0、embed-multilingual-v3.0

**配置步骤：**
1. 进入 **设置** → **Embedding 提供商**
2. 选择提供商
3. 配置设置：
   - **API 密钥**：提供商 API 密钥
   - **模型**：Embedding 模型
   - **维度**：向量维度（关键 - 必须与数据匹配！）
   - **令牌限制**：每个请求的最大输入令牌数

**重要 - Embedding 维度：**
- 上传文档后**无法更改**，除非清除数据库
- 常见维度：1024（Jina、Qwen）、1536（OpenAI 默认）、3072（OpenAI large）
- 如果更改维度，必须：
  1. 创建新工作空间，或
  2. 清除现有数据（文档标签页 → 清除全部）

**推荐 Embeddings：**
- **最佳质量**：text-embedding-3-large（3072 维）
- **平衡**：text-embedding-3-large（1536 维）、jina-embeddings-v3
- **快速本地**：Ollama 配合 qwen2.5-embedding

#### 2.3 Reranker 配置（可选）

Reranker 通过重新评分检索结果来提高搜索准确性。

**支持的提供商：**
- **Cohere**：rerank-english-v3.0、rerank-multilingual-v3.0
- **Jina AI**：jina-reranker-v2-base-multilingual
- **Voyage AI**：rerank-2、rerank-2-lite
- **null**：禁用 reranking

**配置步骤：**
1. 进入 **设置** → **Reranking 提供商**
2. 选择提供商或"null"以禁用
3. 配置 API 密钥和模型
4. 启用"默认使用 Rerank"复选框

**何时使用 Reranking：**
- ✅ 大型文档集合（>1000 个文档）
- ✅ 需要高精度结果
- ✅ 多语言内容
- ❌ 小数据集（<100 个文档）- 可能看不到改进
- ❌ 速度至关重要 - 增加延迟

### 第三步：配置高级参数

使用这些参数微调知识库行为。

#### 3.1 存储配置

**向量存储：**
- **FAISS**（默认）：快速的内存向量搜索
- **Milvus**：可扩展的生产级向量数据库
- **Qdrant**：高性能向量搜索引擎
- **PostgreSQL (PGVector)**：基于 SQL 的向量存储

**图存储：**
- **NetworkX**（默认）：小数据集的内存图
- **Neo4j**：大型知识图谱的生产图数据库
- **Memgraph**：高性能图数据库

**文档状态存储：**
- **JsonKVStorage**（默认）：简单的 JSON 文件存储
- **PostgreSQL**：生产环境的基于 SQL 的存储

**建议：** 除非有 >10,000 个文档，否则使用默认值（FAISS + NetworkX + JsonKVStorage）。

#### 3.2 分块参数

控制文档如何分割以进行索引。

| 参数 | 默认值 | 描述 | 推荐范围 |
|------|--------|------|----------|
| **分块令牌大小** | 1200 | 每个分块的令牌数 | 800-2000 |
| **分块重叠** | 100 | 分块之间的重叠 | 50-200 |
| **最大异步** | 4 | 并行处理任务 | 2-8 |
| **最大嵌入令牌** | 8192 | 嵌入的最大令牌数 | 取决于模型 |

**调优提示：**
- **更大的分块**（1500-2000）：更好的上下文，处理较慢
- **更小的分块**（800-1000）：更快，更细粒度的搜索
- **更多重叠**（150-200）：更好的连续性，更多存储
- **更少重叠**（50-100）：更快的处理，更少冗余

#### 3.3 实体提取参数

控制知识图谱构建。

| 参数 | 默认值 | 描述 |
|------|--------|------|
| **实体类型** | organization, person, geo, event | 要提取的类型 |
| **最大精炼** | 1 | 精炼迭代次数 |
| **实体摘要最大令牌** | 500 | 摘要长度 |

**何时调整：**
- **特定领域**：添加自定义实体类型（例如："product"、"chemical"）
- **高精度**：将 max_gleaning 增加到 2-3（较慢）
- **速度优先**：将 max_gleaning 设置为 0

#### 3.4 查询参数

查询的默认设置（可以在每次查询时覆盖）。

| 参数 | 默认值 | 描述 |
|------|--------|------|
| **Top K** | 60 | 要检索的实体/关系数 |
| **文本单元最大令牌** | 4000 | 上下文窗口 |
| **本地上下文最大令牌** | 4000 | 本地模式上下文 |
| **全局上下文最大令牌** | 4000 | 全局模式上下文 |

#### 3.5 日志配置

- **详细日志**：启用详细日志以进行调试
- **日志级别**：INFO（默认）、DEBUG、WARNING、ERROR

### 第四步：上传和处理文档

#### 4.1 支持的文件格式

- **文档**：PDF、DOC、DOCX、TXT、MD
- **数据**：CSV、JSON、XML
- **代码**：PY、JS、TS、JAVA、CPP 等
- **网页**：HTML、HTM

#### 4.2 上传流程

1. 导航到 **文档** 标签页
2. 点击 **上传文件** 按钮
3. 选择一个或多个文件
4. 点击 **上传**
5. 监控处理状态：
   - **待处理**：排队等待处理
   - **处理中**：当前正在索引
   - **预处理完成**：文本已提取，准备嵌入
   - **已处理**：成功索引
   - **失败**：发生错误（检查日志）

#### 4.3 处理流程

```
上传 → 文本提取 → 分块 → 嵌入 → 实体提取 → 知识图谱构建 → 索引
```

**处理时间：**
- 小文件（<1MB）：10-30 秒
- 中等文件（1-10MB）：1-5 分钟
- 大文件（>10MB）：5-30 分钟

**提示：**
- 一次上传多个文件以进行批处理
- 检查"跟踪状态"以监控进度
- 失败的文档可以在修复问题后重新上传

#### 4.4 文档管理

- **查看文档**：查看所有上传的文档及其状态
- **删除文档**：从知识库中删除文档
- **重新处理**：删除并重新上传以更新内容
- **清除全部**：删除所有文档（需要确认）

### 第五步：查询知识库

#### 5.1 查询模式

知识库支持多种查询模式：

| 模式 | 描述 | 最适合 |
|------|------|--------|
| **local** | 以实体为中心的搜索 | 具体事实、定义 |
| **global** | 关系模式分析 | 趋势、连接、摘要 |
| **hybrid** | 结合 local + global | 全面的答案 |
| **naive** | 纯向量搜索 | 简单的关键词匹配 |
| **mix** | 知识图谱 + 向量 | **推荐默认** |
| **bypass** | 直接 LLM（无检索） | 一般问题 |

#### 5.2 使用检索标签页

1. 导航到 **检索** 标签页
2. 在输入框中输入您的问题
3. （可选）调整查询设置：
   - **模式**：选择查询模式
   - **Top K**：要检索的结果数量
   - **自定义提示**：指导响应格式
   - **启用 Rerank**：切换 reranking
4. 点击 **发送** 或按 Enter
5. 查看带有参考的响应

**查询示例：**
- "产品 X 的主要功能是什么？"
- "总结研究论文中的关键发现"
- "组件 A 如何与组件 B 交互？"
- "列出所有提到的公司及其角色"

#### 5.3 高级查询选项

**自定义提示：**
```
请提供带有代码示例的详细技术说明。
```

**响应类型：**
- "多个段落"
- "单个段落"
- "项目符号"
- "表格格式"

**上下文控制：**
- **only_need_context**：获取原始上下文而不生成 LLM
- **only_need_prompt**：查看发送给 LLM 的提示
- **include_chunk_content**：在参考中查看实际文本块

### 第六步：探索知识图谱

#### 6.1 图可视化

1. 导航到 **图谱** 标签页
2. 查看知识图谱可视化
3. 与图谱交互：
   - **缩放**：鼠标滚轮或捏合
   - **平移**：点击并拖动
   - **选择节点**：点击实体

#### 6.2 图谱功能

- **节点**：实体（人物、组织、地点、事件）
- **边**：实体之间的关系
- **颜色**：不同的实体类型
- **大小**：重要性/频率

#### 6.3 图谱操作

- **搜索**：查找特定实体
- **过滤**：显示/隐藏实体类型
- **布局**：调整图谱布局算法
- **导出**：保存图谱数据
- **全屏**：展开图谱视图

## MCP API 集成

知识库可以通过技能编辑器中的 MCP（模型上下文协议）工具以编程方式访问。

### 可用的 MCP 工具

#### 1. `ragify` - 上传文档

将文档或文本摄入知识库。

**参数：**
```json
{
  "input": {
    "file_paths": ["path/to/file1.pdf", "path/to/file2.txt"],
    "text": "可选的直接文本内容",
    "file_source": "可选的源标识符"
  }
}
```

**返回：**
- 用于监控处理状态的跟踪 ID
- 成功/错误消息

**示例用例：**
- 自动从文件夹上传文档
- 插入抓取的网页内容
- 批量处理研究论文

#### 2. `rag_query` - 查询知识库

从知识库搜索和检索信息。

**参数：**
```json
{
  "input": {
    "query": "主要功能是什么？",
    "mode": "mix",
    "top_k": 60,
    "enable_rerank": true,
    "include_references": true,
    "user_prompt": "提供技术摘要",
    "response_type": "项目符号"
  }
}
```

**返回：**
- 生成的答案
- 带有源文档的参考
- 元数据（使用的令牌、处理时间）

**查询模式：**
- `local`：以实体为中心的检索
- `global`：关系分析
- `hybrid`：组合方法
- `naive`：仅向量搜索
- `mix`：知识图谱 + 向量（推荐）
- `bypass`：无检索的直接 LLM

**示例用例：**
- 构建问答聊天机器人
- 自动化研究助手
- 文档分析流程

#### 3. `ragify_async` - 异步上传并通知

使用后台处理和完成通知上传文档。

**参数：**
```json
{
  "input": {
    "file_paths": ["large_file.pdf"],
    "on_complete": true,
    "notify_task_id": "task_123",
    "timeout_seconds": 600,
    "poll_interval_seconds": 15,
    "notification_message": "处理完成！"
  }
}
```

**返回：**
- 带有跟踪 ID 的即时响应
- 后台监控在完成时发送通知

**示例用例：**
- 长时间运行的文档处理
- 无阻塞的批量上传
- 自动化工作流

#### 4. `wait_for_rag_completion` - 等待处理完成

阻塞直到文档处理完成。

**参数：**
```json
{
  "input": {
    "track_id": "abc123",
    "timeout_seconds": 600,
    "poll_interval_seconds": 15,
    "max_retries": 3
  }
}
```

**返回：**
- 完成状态（成功/失败/部分）
- 已处理/失败的文档计数
- 文档详情

**示例用例：**
- 同步工作流
- 确保文档在查询前准备就绪
- 错误处理和重试逻辑

#### 5. `in_browser_upload_file` - 通过浏览器上传

通过浏览器自动化上传文件（用于基于网页的上传表单）。

**参数：**
```json
{
  "input": {
    "driver_type": "cdp",
    "browser_type": "chrome",
    "href": "https://example.com/upload",
    "upload_file_path": "/path/to/file.pdf"
  }
}
```

**示例用例：**
- 自动化表单提交
- 带文件上传的网页抓取
- 测试上传功能

## 故障排除

### 常见问题

**1. 维度不匹配错误**
```
错误：FAISS 维度不匹配
```
**解决方案：** 
- 使用正确的维度创建新工作空间，或
- 清除所有文档并重新配置嵌入维度

**2. API 密钥错误**
```
错误：无效的 API 密钥
```
**解决方案：**
- 在设置中验证 API 密钥
- 检查提供商账户状态
- 更新密钥后重启应用程序

**3. 处理卡住**
```
文档状态：处理中（30+ 分钟）
```
**解决方案：**
- 检查 LightRAG 服务器日志（设置 → 查看日志）
- 重启 LightRAG 服务（设置 → 重启服务）
- 验证文件未损坏

**4. 空响应**
```
查询返回无结果
```
**解决方案：**
- 确保文档已完全处理（状态：已处理）
- 尝试不同的查询模式（mix、hybrid、naive）
- 增加 top_k 参数
- 检查查询是否匹配文档内容

**5. 查询缓慢**
```
查询耗时 >30 秒
```
**解决方案：**
- 仅对重要查询启用 reranking
- 减少 top_k 值
- 使用更快的嵌入模型
- 考虑升级存储后端（FAISS → Milvus）

## 最佳实践

### 1. 工作空间组织
- 为不同项目创建单独的工作空间
- 使用描述性名称："法律文档"、"技术规范"、"研究_2024"
- 不要在一个工作空间中混合不相关的内容

### 2. 文档准备
- 上传前清理文档（删除页眉/页脚）
- 使用一致的格式
- 将非常大的文件（>50MB）拆分为较小的部分
- 在文件名中包含元数据

### 3. 模型选择
- **开发**：使用快速、便宜的模型（GPT-3.5、Qwen Turbo）
- **生产**：使用高质量模型（GPT-4、Claude 3.5）
- **隐私敏感**：使用本地模型（Ollama）

### 4. 查询优化
- 从"mix"模式开始，根据结果调整
- 使用具体问题，而不是模糊查询
- 利用自定义提示进行格式化
- 对关键查询启用 reranking

### 5. 性能调优
- 监控处理时间并调整分块大小
- 为规模使用适当的存储后端
- 仅在调试时启用详细日志
- 定期清理未使用的文档

## 附录

### A. 配置文件位置

- **设置**：`<workspace>/resource/data/lightrag.env`
- **文档**：`<workspace>/rag_storage/<workspace_name>/`
- **日志**：检查应用程序日志目录

### B. API 端点

LightRAG 服务器默认运行在 `http://localhost:20443`。

- `POST /documents/upload` - 上传文件
- `POST /documents/text` - 插入文本
- `POST /query` - 查询知识库
- `GET /documents/track/{track_id}` - 检查处理状态
- `GET /graph/entities` - 获取实体
- `GET /graph/relationships` - 获取关系

### C. 术语表

- **RAG**：检索增强生成
- **Embedding**：文本的向量表示
- **实体**：命名对象（人物、地点、事物）
